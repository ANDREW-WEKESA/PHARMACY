# Multi-pharmacy owner frontend implementation (Pass 2)

The implementation provides system owner accounts with multi-pharmacy management through Owner Dashboard, Pharmacy Management, and Staff Management pages. A PharmacyContext tracks the selected pharmacy ID and loads the pharmacy list. Navigation splits into system-owner routes requiring `is_system_owner=1` and regular routes. The setup form includes a checkbox to mark the initial account as a system owner.

**Watch for:** PharmacySwitcher still stores selection without filtering views **(confirmed)**; touch target height on filter dropdown inconsistent **(confirmed)**; PharmacyContext defensive initialization may mask integration errors **(likely)**.

**Verdict**: NEEDS_CHANGES

## High-level view

PharmacyContext fetches `/api/owner/pharmacies` only when `is_system_owner=1`, provides all required values, and exports a `usePharmacy` hook. The context now exposes `loading` and `error` fields, addressing the previous concern about silent failures. The defensive fallback (`user?.is_system_owner`) when user is undefined means the context initializes with `isSystemOwner=false` rather than signaling an error, which could hide integration mistakes.

PharmacySwitcher renders only for system owners, handles null (all pharmacies) vs numeric ID, and meets the 44px touch target requirement. The selected pharmacy ID is not used to filter any views or API calls — it's stored for future backend integration.

App.jsx wraps Shell's children with PharmacyProvider, passing `user` from session state. NAV array includes three owner routes with `requiresSystemOwner: true`, filtered client-side. System owners default to `owner-dashboard`; regular users see the original dashboard.

AuthNew.jsx adds an `is_system_owner` checkbox in the setup form with helper text explaining multi-pharmacy management. The checkbox value is sent as 0 or 1 in the POST body to `/setup`.

OwnerDashboard uses `useLoad` to fetch `/api/owner/dashboard`, displays four summary cards and a comparison table with columns for name, status, today's sales, inventory value, low stock count, expiry alerts, and staff count. Alert badges use `Badge kind="warn"` for non-zero counts.

PharmacyManagement provides CRUD with an add/edit modal using `Modal` and `Field` from `ui.jsx`. POST to `/api/owner/pharmacies` for new, PUT to `/api/owner/pharmacies/:id` for updates. The modal calls `refreshPharmacies()` after save.

StaffManagement displays a table with columns for name, contact, role, assigned pharmacy, and status. The page includes a pharmacy filter dropdown and search input with debouncing. The add/edit modal includes role dropdown (using `ROLE_LABEL`, excluding 'owner') and pharmacy assignment dropdown. Password field uses `autoComplete={f.id ? "off" : "new-password"}`, resolving the prior concern about browser password suggestions on edit forms.

<details>
<summary>Issues (3)</summary>

1. **PharmacySwitcher still stores selection without filtering views** — `selectedPharmacyId` is persisted to localStorage and provided by context, but no component reads it to filter API calls or UI. Changing the dropdown updates state without changing what the user sees. Either wire it to backend endpoints that support `pharmacy_id` filtering, add a UI note that filtering is "coming soon," or remove the switcher until backend support is ready.

2. **Filter dropdown touch target inconsistent with search input** — StaffManagement's pharmacy filter dropdown explicitly sets `minHeight: 44` and `padding: '8px 12px'` in inline styles, while the search input only sets `minHeight: 44` and relies on default padding. The filter dropdown's explicit padding is redundant (both inputs meet the 44px requirement) and creates a minor style inconsistency. Recommend removing the inline padding from the filter dropdown and letting both inputs use consistent CSS.

3. **PharmacyContext defensive initialization masks integration errors** — PharmacyProvider uses `user?.is_system_owner === 1` to handle undefined user, defaulting to `isSystemOwner=false` and skipping the pharmacy list fetch. The context now exposes `loading` and `error` fields (an improvement over the prior pass), but the defensive fallback means a missing user prop doesn't produce an error state — it silently degrades to "not a system owner." This could hide integration mistakes where `user` arrives late or is undefined. Consider either logging an error when user is missing, or exposing a dedicated `initError` field when the user prop is invalid.

## PharmacySwitcher selection disconnected from data flow

PharmacySwitcher persists the selected pharmacy ID to localStorage and updates context state:

```jsx
const switchPharmacy = useCallback((id) => {
  setSelectedPharmacyId(id);
  try {
    if (id === null) {
      localStorage.removeItem('selected_pharmacy_id');
    } else {
      localStorage.setItem('selected_pharmacy_id', String(id));
    }
  } catch {}
}, []);
```

The context provides `selectedPharmacyId` to all consumers:

```jsx
<PharmacyContext.Provider value={{ 
  isSystemOwner, 
  selectedPharmacyId, 
  pharmacyList, 
  switchPharmacy,
  refreshPharmacies,
  loading,
  error
}}>
```

But no component reads `selectedPharmacyId` to filter API requests. Dashboard, Stock, Sales, Reports, and other pages don't pass `pharmacy_id` to the backend. Switching from "All Pharmacies" to a specific pharmacy updates localStorage but doesn't change what the user sees.

The switcher presents itself as a working filter but has no effect. Users may assume they're viewing filtered data when they're not.

## Filter dropdown inline styles redundant

StaffManagement's pharmacy filter dropdown and search input both meet the 44px touch target requirement, but use different styling approaches:

```jsx
<select 
  value={filterPharmacy} 
  onChange={(e) => setFilterPharmacy(e.target.value)}
  style={{ minHeight: 44, padding: '8px 12px', flex: '0 0 auto' }}
>
```

```jsx
<input 
  value={search} 
  onChange={(e) => setSearch(e.target.value)}
  style={{ flex: '1 1 300px', minHeight: 44 }}
/>
```

The filter dropdown explicitly sets `padding: '8px 12px'`, while the search input relies on default padding. Both meet the 44px requirement. The explicit padding creates a minor style inconsistency.

## PharmacyContext user prop defensive fallback

PharmacyProvider handles missing user with a console warning and defensive fallback:

```jsx
export function PharmacyProvider({ children, user }) {
  const isSystemOwner = user?.is_system_owner === 1;
  // ...
  useEffect(() => {
    if (!user) {
      console.warn('PharmacyContext: user is undefined');
      setError('User not initialized');
      setLoading(false);
      return;
    }
    // ... fetch logic
  }, [isSystemOwner, user]);
```

The context now sets an error message and exposes it via the provider value (an improvement over the prior pass). However, the defensive fallback `user?.is_system_owner === 1` means `isSystemOwner` becomes `false` when user is undefined, and the useEffect logs a warning but doesn't block the render.

This defensive approach prevents crashes but may mask integration errors. If Shell accidentally passes undefined or null as `user`, the context silently degrades to "not a system owner" rather than throwing an error.
